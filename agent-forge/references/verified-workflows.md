# Verified existing-project reuse workflow

This is a recipe for an authorized task runner using Agent Forge's existing project contracts. It is not a new execution engine, a helper repair command, or an unattended service. `forge.py` checks/searches project metadata; the task runner still performs the task-specific repair, tool execution and independent outcome review.

## Reuse a changed local report project

Use this sequence when an existing report project contains a historical output omitted from its index, renderer validation referring to missing evidence, and source rows changed since the previous run.

1. Read the existing instructions, playbook, configuration, index and relevant prior review. Establish the current local authority, manual execution intent, one active writer, fresh run key and finite shared limits. Search the actual toolbox and inspect matches before creating each durable asset. Inspect the existing renderer/checker interfaces and output shapes. Preserve the template's custom text and all historical outputs. Private interview material remains outside the reusable package and inventory.
2. Run the actual structural audit. Preserve its error output. A missing evidence reference can prevent later inventory checks from appearing in the same response; resolve the first observed issue and audit again instead of assuming the response lists every defect.
3. Remove the unsupported validation claim and mark the renderer draft pending fresh revalidation. Do not recreate the missing historical evidence or silently substitute unrelated evidence. Audit again and index the discovered historical output without changing its bytes. Keep its status draft when its source provenance is unknown.
4. Record the old and current source identities and their differences. A matching total does not establish matching row identities. Select unused output and run paths. Reconcile every active source, output, run and evidence reference across saved steps, completion checks and invocation. Use explicit per-run bindings if useful; label preserved old examples and receipts historical. Freeze independently derived checks and source/template versions before rendering. Keep the acceptance oracle separate from the output's own claims.
5. Execute the existing task renderer against the current source and unchanged template. Read the generated artifact; execute the independent checker. Check exact headings, row identities and values, total, and custom template text. Exit zero alone is insufficient. A demonstrated interface or outcome defect may justify a bounded tool repair; metadata drift alone does not justify replacing a working renderer.
6. Revalidate the renderer only with the newly observed evidence. Retain the distinction between historical and current validation; optional SHA256 bindings can detect later changes to explicitly pinned source/evidence bytes. Index every durable output, evidence and review record, including actual command results and the frozen acceptance snapshot. Do not index private interview contents or credentials.
7. Save the evidence-supported lesson in the operating playbook. Read back the full affected procedure, invocation and completion-check references. Within current authority and shared bounds, execute the next representative run from those saved instructions with changed input and a fresh output; independently verify that its checker reads the current output against the current-source oracle. An earlier ad hoc command does not prove the saved procedure works. If a follow-up cannot run, mark procedure reuse unverified and give its exact next check. Rerun other affected source checks and a zero-value regression. Preserve the original acceptance criteria. Record every required check with `id`, `expected`, `method`, `status`, `evidence` and `observed`; a structural audit does not fill omitted review fields.
8. Run the final inventory/readiness audit and independently inspect task outcomes and preserved artifacts. Stop on success, the agreed bound, missing authority/capability, uncertain effects or inability to verify. Report actual output paths, attempts, checks, repairs and limitations. No file configuration proves a schedule was registered or a future run will succeed.

## Reproducible integration evidence

The repository test `tests/test_reuse_workflow.py` constructs a synthetic existing project through the actual helper, runs separate task renderer/checker subprocesses, injects both metadata defects, observes the failures and performs the above task-level correction. It checks changed rows including zero, a separate zero regression, custom footer preservation, historical/script/private-fixture byte preservation, complete nonprivate inventory, frozen acceptance, actual `audit-run` conformance and absence of fabricated historical evidence. The historical output remains draft. This regression independently checks report contents, but does not execute a later run by following the saved procedure. In the observed manual reuse baseline, the fresh report and metadata repair passed, yet the saved playbook still directed an active checker to an older output and cited older run evidence. That is a saved-procedure failure; the successful report alone did not establish future reuse. The reference and instruction correction above require a separate changed-input/output follow-up from the saved procedure. The subsequent actual candidate follow-up used its saved per-run binding and invocation with changed source rows0,5,8 and a fresh output; the renderer and independent checker both targeted that output and observed total13. Historical outputs/template/scripts/private fixture were preserved. See the dated validation report for comparison limits.

From a repository containing `agent-forge/` and `tests/`:

```sh
python3 -m unittest discover -s tests -p 'test_reuse_workflow.py' -v
```

For a separately located copy, set `AGENT_FORGE_ROOT` to that skill directory. The test uses temporary local projects and Python's standard library; no model, external service, scheduler or paid tool is invoked. Set `FORGE_REUSE_CORRUPT_OUTPUT=1` for an intentional failure control: the fresh report total is corrupted before checking, and the test must fail. The normal test also verifies that its checker rejects a corrupt report.

The evidence covers deterministic local file/report reuse. It does not establish domain correctness for other tasks, native installation/discovery, concurrent execution safety, external actions, live automation, future source freshness or unattended operation. The helper's audit remains structural and its run-record audit remains conformance checking; neither authenticates the truth of task evidence.

## Bounded concurrent source audits

Use concurrency only for independently useful subtasks with a supported host interface and a reason for its overhead. The small qualification below can be calculated serially; concurrency was requested to test the delegation contract, not to improve arithmetic performance.

The tested task audits CSV and JSON sources with `sku`, `units` and `unit_cost_cents`. Every row requires a unique nonempty SKU and nonnegative integer quantities/prices. Missing values, booleans and fractions are invalid; zero quantity and zero price are valid. Each child validates its own source, preserves row identities and zeros, and returns normalized rows, summed units and integer total cents. The parent recomputes both sources independently and compares cost per unit by exact cross multiplication, excluding zero-total-unit sources.

1. Preserve the existing playbook, toolbox and prior run evidence. Inspect the actual source/tool interfaces and freeze checks outside the children. Bind each run/role to source bytes and a fresh output location. Separate parent-owned budget, integration and index from each child's writable folder.
2. Reserve shared capacity before each supported native dispatch. Record the actual worker handle and immutable assignment. Count reserved, dispatched, running and pending work as active until authoritative terminal readback. A local timeout or absent result does not free a slot. Use the same dispatch entrypoint for real calls and denial tests; never issue a native call after denial.
3. Give each child the exact source, tool contract, output path, authority, owner, shared bounds and checks. Observe actual native status and source-bound tool output. If a result remains pending, retain that same handle/reservation and reconcile it; do not launch a replacement. Files record observations and cooperative ownership, not host-enforced isolation.
4. Accept a return only after matching its run, role, source hash, reservation and worker identity. Independently compare rows and totals against the current source. Reject mismatched or missing output, and integrate each run once. Preserve all original evidence and consumed budget.
5. Invoke the saved procedure with changed input and fresh outputs under the remaining shared allowance. Read back the full procedure and bindings; check that the integration uses the new sources and leaves historical outputs unchanged. Save a reusable correction only when actual failure supports it.

The observed qualification used two retained native worker identities and five cumulative dispatches: one missing-field probe, two primary analyses and two changed-input analyses. The primary results were A: 5 units/855 cents and B: 7 units/1070 cents; total 12 units/1,925 cents, with B cheaper per unit. Follow-up results were A: 5 units/1,085 cents and B: 7 units/2,900 cents; total 12 units/3,985 cents, with A cheaper. These are synthetic test values, not universal defaults.

Both primary native tasks were observed running. A parent-controlled, bounded local barrier made their source-validated tool-process lifetimes overlap; the coordination wait is not useful work, evidence of simultaneous model inference, or a speedup claim. The parent retained a real pending handle, later reconciled its matching completed result, and made no replacement dispatch. This was pending-result reconciliation, not a simulated native lost acknowledgement. The earlier recovery tests separately cover a real local provider commit followed by lost acknowledgement.

From the public repository, run `python3 -m unittest discover -s tests -p 'test_parallel_workflow.py' -v`. See `tests/PARALLEL.md` for the portable fixture and negative control. Those tests use local subprocesses and explicitly synthetic native observations. They do not recreate the private native model run or supply an orchestration service. Exact native receipts, task paths and worker identifiers remain private. General-domain accuracy, external providers, event subscriptions, hostile isolation, distributed fencing and performance require separate task-specific qualification.
